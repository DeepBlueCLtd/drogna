# Adversarial review

A session that wrote a change is the worst reviewer of it: every assumption it made
while writing is still loaded, and it will read the diff as confirmation. This skill
hands the change to subagents that have never seen the conversation. What comes back is
a map of where to look, not a substitute for looking.

The value is in the independence. **Do not brief the subagents on the change.** Do not
explain what it was meant to do, why a choice was made, or which part you are unsure
about — every sentence of that re-imports the blind spot the skill exists to route
around. They get the diff, the base, and nothing else.

## 1. Resolve the target

- An argument that is a number → that pull request. Get its head branch, base branch and
  body with `mcp__github__pull_request_read`.
- An argument that is a branch name → that branch against `main`.
- No argument → the current branch against `main`, and find its open pull request with
  `mcp__github__list_pull_requests` (head filter). If there is no open pull request,
  say so and run the review anyway, reporting to the terminal only.

Then materialise the diff, from the merge base so that base-branch commits are not read
as the author's work:

```sh
git fetch origin main <head-branch>
BASE=$(git merge-base origin/main origin/<head-branch>)
git diff $BASE origin/<head-branch> > <scratchpad>/pr-<n>.diff
git diff --stat $BASE origin/<head-branch>
```

If the diff is empty, stop and say so — a merged or already-rebased branch produces one.

## 2. Attack it

Spawn **two** `pr-adversary` subagents in one message so they run concurrently, each on
the same diff with a different remit. Two independent passes disagree usefully; one pass
is a single sample.

- **Pass A — correctness.** Faults, unreachable guarantees, broken invariants,
  constitution violations that the gates do not catch.
- **Pass B — simplicity and the record.** Machinery that earns nothing, duplicated
  state, and the record-versus-tree checks: ticked tasks, spec claims, PR body, blog
  entry, title form.

Both produce the assumptions-and-decisions map; both are told the repository root, the
diff path, the base SHA and the head branch. Nothing else.

## 3. Verify before you publish anything

Every finding from either pass goes to a `pr-finding-verifier` subagent — one per
finding, spawned concurrently, each given only that finding and the head branch. This
step is the price of posting to a public thread: an unverified adversarial pass posts
false positives beside the author's work, and a reviewer who reads two wrong comments
stops reading the third.

Merge the verdicts:

- **CONFIRMED** → an inline comment on the PR.
- **REFUTED** → dropped entirely. Do not post it, do not mention it as "considered".
- **UNRESOLVED** → one line in the review body, under a heading that says it is
  unresolved. Never an inline comment.

De-duplicate where both passes found the same fault; keep the better failure scenario.

## 4. Run the gates yourself

Before posting, run `pnpm gates` (and `pnpm check` if the diff touches `app/src`) on the
head branch. A finding the gates already catch is noise on the thread — CI says it
louder. A finding the gates *should* catch and do not is the most valuable thing this
skill can produce: report it as a gap in `scripts/gates.registry`, and say which gate
would have caught it.

## 5. Post the review

Use the pending-review flow: `mcp__github__pull_request_review_write` with `create`,
then `add_comment_to_pending_review` per confirmed finding, then `submit_pending` as
**COMMENT** — never `REQUEST_CHANGES`, and never `APPROVE`. This is a machine's opinion
offered to a human reviewer, and approval is not its to give.

Body, in this order:

1. **Assumptions and design decisions** — the merged map, ranked by how much breaks if
   the assumption is wrong. This is the part a reader uses to decide where to look, so
   it goes first even when there are findings.
2. **Confirmed findings** — one line each, pointing at the inline comments.
3. **Unresolved** — with what would settle each.
4. **Checked and sound** — what the passes went looking for and did not find.
5. One sentence naming the model, the two passes, and that findings were verified
   against head before posting.

End the body, and every inline comment, with the attribution footer:

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Then print a short ranked list in the terminal: the three things worth opening the diff
for, in order. That list, not the review, is what the human actually reads first.

## What this does not do

It does not fix anything, approve anything, or replace reading the change. It has not
run the app: a finding about what the shell shows is a claim about a running system, and
the instance link in the pull request is the system (`CLAUDE.md`, "Showing the work").

## Calibrating it

A reviewer that has never been seen to miss a fault is worth nothing — the same rule
this repository applies to its gates. Before trusting a clean report, plant a fault on a
scratch branch (an unmarked `Date.now()` in a backend component, a panel importing
`app/src/backend` directly, a snapshot edited by hand), run the skill against it, and
check that the passes name it. Record what was planted and what was caught in the pull
request that changes this skill. A clean report on a diff you know to be broken means
the prompt has drifted, not that the code is sound.
