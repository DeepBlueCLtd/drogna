# Working on drogna

drogna is a demonstration harness, at Version 2: a synthetic ocean, sensors that sample
it, a forecast loop that assimilates what they report, and a query layer that serves the
result through OGC API-EDR and SensorThings — all of it genuine programs running in one
browser page, behind a wire-protocol seam (ADR-0027). Everything in it is deliberately
fake and says so.

Two lessons head this file because Version 1 paid for them and every trap it recorded
was an instance of one of them:

1. **The tree is the authority and the record is a claim about it.** Where the two
   disagree, check the tree, then fix the record. This applied to `tasks.md` files
   (196 of 252 "unticked" tasks turned out done), and then to this file's own opening
   paragraph. Tick tasks as you go, and write the reason at the moment you decide not
   to do something — the reason is the part that cannot be reconstructed later.
2. **A check that has never been seen to fail is worth nothing.** Plant the violation,
   see it caught, revert it, and say so in the commit message. Two of V1's original
   four gates reported a file of deliberate violations as clean; a regression test for
   a real fault once passed against the unfixed code. When a test passes on first
   attempt, be suspicious rather than pleased — and prefer a bound derived from
   something on disk over a number typed into a test.

## Commands

Everything runs from one pnpm workspace at the repository root; no Python, no
containers, no daemon (SRD-v2 NFR-01).

```sh
pnpm install
pnpm check        # typecheck, lint, unit tests, gates — what CI runs
pnpm gates        # the constitution gates alone (scripts/gates.registry)
pnpm generate     # regenerate app/src/generated/ from contracts/ masters
pnpm -C app dev   # the shell, live, at a local URL
pnpm -C app build # the static site V2 delivers
pnpm site:build   # the published site, into site/build/ (ADR-0031)
```

`pnpm gates` runs the gates listed in `scripts/gates.registry`, one per line. **A new
gate is a line appended to that registry.** Never edit the runner — it names no gate,
which is what lets a feature add one without touching the others.

## Working practices that have earned their place

- **Stage first, verify the staged tree, then commit.** `git add -A` swept in-flight
  work into three separate red CI runs in V1. Where agents write concurrently, verify
  the snapshot rather than the working tree.
- **Some files are shared and append-only**: `scripts/gates.registry`,
  `contracts/schemas/` (a master is amended, never casually rewritten), `pnpm-lock.yaml`
  (regenerated by the tool, never edited). Append, never rewrite.
- **Boundary shapes are generated, never hand-written.** Add the master under
  `contracts/schemas/` (or the OpenAPI document), run `pnpm generate`, commit the
  output under `app/src/generated/`. The drift gate fails the build when the committed
  output no longer matches a fresh generation.
- **No import across the seam.** Front-end (`app/src/shell`, `app/src/panels`) and
  backend (`app/src/backend`) may share only `app/src/seam` and `app/src/generated`.
  The import-boundary gate enforces this; do not fight it, restructure instead.
- **A specification that disagrees with the code is not automatically wrong.** Four
  times in V1 the code was right and the requirement loose, and once the reverse.
  Establish which before amending either; record genuine open questions as open.
