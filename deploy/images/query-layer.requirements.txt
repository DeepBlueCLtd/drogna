# Python dependencies of the query layer image (C-09).

# Pinned to an exact released version rather than a range. The bespoke EDR trajectory
# provider (FR-50, ADR-0003) subclasses pygeoapi's provider base class and rests on two
# surfaces that carry no compatibility promise: BaseEDRProvider.__init_subclass__, which
# builds the advertised query types from the subclass's own methods, and the query_args
# dict the framework passes to them. Moving this version means re-running the feature 002
# spike -- see the "Shelf life" section of spikes/edr-trajectory/FINDING.md, which names
# this as one of the events that invalidates its result.
pygeoapi==0.20.0

# ---------------------------------------------------------------------------------------
# The FR-51 pin: Shapely 2.1 or later, built against GEOS 3.12 or later.
#
# This is a silent-failure guard. It cannot be relaxed, and the constraint on the last
# line is only half of it -- read to the end before changing either half.
# ---------------------------------------------------------------------------------------
#
# What it guards. An EDR trajectory query carries its per-vertex arrival times in the M
# ordinate of a WKT LINESTRING M or LINESTRING ZM. pygeoapi parses the coords string with
# shapely.wkt.loads before any provider code runs and hands the parsed geometry on
# untouched. If M does not survive that parse, the arrival times are gone before drogna
# sees them at all: FR-20 -- conditions forecast for the moment of arrival at each point,
# rather than conditions at query time -- fails, while the response stays structurally
# correct and plausible.
#
# Nothing raises. Feature 002 measured this rather than citing it, and found three failure
# modes rather than the one FR-51 names. Shapely and GEOS fail independently, which is why
# a version constraint on Shapely alone is not sufficient: the GEOS a wheel was built
# against decides two of the three.
#
#   Shapely >= 2.1  GEOS <  3.12   M is returned as NaN. This is the case FR-51 describes.
#                                  Note that shapely.has_m raises
#                                  UnsupportedGEOSVersionError here rather than returning
#                                  False, so a guard written in terms of it errors out
#                                  instead of failing informatively.
#
#   Shapely 2.0.x   GEOS >= 3.12   M is not NaN but absent: no include_m parameter and no
#                                  has_m attribute exist. LINESTRING M yields (x, y)
#                                  tuples; LINESTRING ZM yields (x, y, z) and round-trips
#                                  out as LINESTRING Z. This is the published pygeoapi
#                                  image as it ships today, and therefore the mode this
#                                  image actually has to correct. A check asserting only
#                                  "M is not NaN" passes here while the times are already
#                                  gone.
#
#   Shapely 2.0.x   GEOS <  3.12   Worse than either. LINESTRING M comes back as a
#                                  LINESTRING Z whose Z values are the timestamps, with
#                                  has_z True -- a Unix timestamp promoted into the depth
#                                  axis, where a provider reading Z as elevation takes
#                                  1788220800 for a depth in metres.
#
# The evidence: spikes/edr-trajectory/FINDING.md, run 26 August 2026, which records the
# probe output for all three combinations; and docs/adr/0003-bespoke-edr-trajectory-
# provider.md, which carries the same table as the decision this pin implements.
#
# Why the constraint below is only half the guard. The published Shapely wheels bundle
# GEOS, so which GEOS this image ends up with is a property of the built artefact and not
# of anything a requirements file can express. query-layer-pin-check.py runs during the
# build, reads both versions out of the installed package, then parses a LINESTRING ZM and
# asserts that the M ordinates come back exactly and that Z is still the elevations --
# behaviour, not version numbers. The build fails if they do not. The two halves travel
# together; removing either leaves the failure silent again.
#
# If you are tidying dependencies and this looks like a stale pin: the cost of relaxing it
# is not a failed build. It is a trajectory response returned with HTTP 200 whose values
# are the whole route evaluated at a single time, which nobody inspecting the response can
# tell from a correct one. Run the FR-51 tests owned by features 002 and 008 before
# touching this line, and read the finding named above first.
#
# The upper bound is a deliberate stop rather than a known incompatibility. Both halves of
# this pin are properties of a built wheel, so a Shapely major release is precisely the
# event that could reintroduce one of the modes above. Lift it by testing, not by
# assumption.
shapely>=2.1,<3

# The database driver the SensorThings provider reads the observation store through.
#
# `PostgresRowSource._connect` imports psycopg lazily, so that the projection, the path
# grammar and the query options can all be tested in a workspace carrying neither a driver
# nor a database — which they were, thoroughly, and all of them passed. What no test could
# see is that the image never installed it: the `except ImportError` beside that import
# carried `# pragma: no cover - the image installs it`, and the image did not.
#
# So every entity set answered 400 with "no database driver is installed, so the observation
# store cannot be read" — a message written for a case its author believed could not happen
# in the image, arriving from the image. It was invisible until the store had something in
# it worth asking for.
#
# `[binary]` and this floor to match services/ingest, which reads the same store through the
# same driver; two spellings of one dependency is how they drift.
psycopg[binary]>=3.2
